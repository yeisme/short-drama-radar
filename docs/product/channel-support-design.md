# Radar 渠道支持与能力补齐设计

本说明基于 2026-09-14 本地源码和小红书上游核对，属于产品设计建议，不是机器状态、任务证据或已接入声明。渠道要求必须保留；分批实现只调整次序。后续具体实现进入本项目 OpenSpec，由 CLI 创建 change 并管理任务。

## 归属与目标

归属判定为 fit：渠道适配、来源资格、观测、指标、证据、简报由 short-drama-radar 持有。DSH 展示为 split-owner，归 agent/harness-plugins，通过既有 MCP/服务投影消费；不复制 Radar 数据库。外部采集工具是可替换输入后端，不持有 Radar 事实真源。

必需能力包括国内外渠道矩阵、逐来源接入设计、小红书 xiaohongshu-mcp 支持、持续观测、渠道诊断、断源恢复和可核查简报。真人短剧、漫剧、区域与语言覆盖保留；未知制作方式不得推断为 AI。既有个人推荐与 card.v1 保持兼容。

## 当前事实与缺口

- 已有抖音、小红书旧采集适配器、浏览器兜底、人工 CSV，以及市场观测/来源/信号/简报/补看/关注/回顾/MCP 本地软件面。
- src/adapters/agentreach-xhs.ts 已路由 OpenCLI、xiaohongshu-mcp、xhs-cli，支持登录探测与 search_feeds；默认关键词为“短剧”，规范化最多保留 30 条。未形成详情、评论、作者观察与持续复采的完整渠道合同。
- 当前小红书规范化读取扁平标题与数值型互动字段。上游 Feed 使用 noteCard.displayTitle、noteCard.interactInfo 和字符串互动数。按上游结构构造的一条合成笔记，经现有 normalizeXhsItems 得到零条；这是本地兼容复现，不是实际登录采集结果。
- 新市场来源初始化为 18 个 planned 候选。红果/ReelShort/DramaBox 有目录文件导入路径；不是自动在线连接器。market observe 和 market canary report 当前明确拒绝为 capability_unavailable。
- import-legacy 保留原快照时间，但因旧快照缺少 live/fixture 标志，保守导入为 manual，不能积累真实来源资格。新采集必须从入口记录 origin，不能事后把旧数据改成 live。
- 产品文档还存在局部状态过期陈述。功能可用性以源码和实际 CLI 为准，后续交付需统一文档。

## 逐渠道必须设计的合同

每个渠道必须明确平台与来源身份、采样角色、目标地区/语言、接入后端与固定版本、登录/权限前置、支持动作、查询与分页范围、指标定义、采样频率、数据新鲜度、超时与恢复、替代输入、真实验收方式。渠道可支持多个后端，但一个来源修订必须固定实际后端与采样口径；切换后端后重新判断可比性。

连接器只产生可校验的观测输入，经现有应用服务落库，再进入分析和简报。扩展市场管线，不把其他平台硬塞进旧两平台 RawItem 或 card.v1。首先复用现有 Adapter、market repository、运行回执和调度设施，仅添加必需的衔接，避免建立另一套调度服务。

同时记录采样发生时间、平台发布时间、稳定对象 ID、查询/排序/范围及 source revision。合法空结果、响应结构变化、登录失败、超时、配额耗尽、部分页面和服务离线必须可区分。后端子进程要有实际超时终止，不能只传一个未必生效的超时参数。

采样计划需区分发现新候选和复采已知对象；同一笔记的两次观测才可能计算互动增量。保留零值与未知值区别；缩写数值如“1.2万”带舍入语义，不能当精确计数。平台搜索排序变化、评论截断或后端更换会影响比较，必要时输出不可比。点赞/收藏不转成播放量，各平台不合成全球热度总分。

## 小红书 xiaohongshu-mcp 首个完整切片

本次核对上游 xpzouying/xiaohongshu-mcp，commit 为 aad2a3d249a347859975ce3b76d3442c4a027780。实现时需固定测试版本并以实际 tools/list 和 inputSchema 检查能力；不根据工具名称推断权限。

1. 保留已有 Agent Reach 路由，增加明确后端选择的设计，满足指定 xiaohongshu-mcp 的需求；所选后端不可用时显式说明，不静默换采样口径。
2. 用 check_login_status 诊断，扫码由操作者完成。登录/浏览器状态归用户级工具配置，不由 Radar 普通库持有。
3. 使用 search_feeds 的关键词和实际支持的 filters，分开最新、互动排序和固定主题集合；list_feeds 是个性化推荐样本，单独标注偏差，不混作全站榜。
4. 映射 Feed 的 noteCard.displayTitle、user、interactInfo；处理上游响应与 MCP 内容包裹的真实形状，保留旧后端兼容。先确认成功响应，再对结构做显式校验，避免将错误文本解析成空榜。
5. 对有界候选调用 get_feed_detail，补正文、发布时间和有限评论。上游要求 feed_id 与 xsec_token；临时访问材料只在适配器内短暂使用，禁止写入日志、证据、URL 投影或普通观测。失效后通过原发现路径刷新，不能盲目重放无限次。
6. user_profile 可为作者观察提供可选读取；先按当前 schema 确认所需引用。详情与评论设每次上限，记录截断与覆盖范围，评论摘要不能声称代表全部观众。
7. 按固定时间复采稳定 ID，生成 market observation，并保留 origin、来源修订、批次与脱敏证据关联。旧个人榜单继续由既有兼容路径消费。
8. Radar 仅读取上游工具子集。publish、点赞、收藏、发评论、删 cookie 不属于采集流程；Radar 内部 saved 反馈不映射为小红书站内收藏。

## 资格启动、运维与验收

来源资格与运行健康分开。需补齐一个有界、显式授权的验证采样阶段：planned 来源先核对身份，再执行验证采样和人工检查，积累现有规则要求的七日证据，最后形成资格决定。生产定时观察才要求正式资格。这样不会陷入“未合格不能采样、未采样不能合格”的循环；验证样本不能让面向用户的覆盖提前显示成熟。

qualified 的显式晋级及撤回需要 revision、资格证据与回执；来源变更使资格重新评估。补 market canary report 的实际软件入口，才能消费十四天真实数据；等待十四天本身不会实现该命令。

运维体验应提供逐渠道的配置状态、后端与版本、最近成功/失败、下次采样、覆盖缺口和可执行恢复步骤，复用 doctor/source gaps/run receipt。将“没有新变化”与“没有采到”清楚分开；失败日纳入试用分母。DSH 应读取这些状态，通过原回执恢复，读取不得触发采集重放。

先完成小红书兼容与 market 验证样本入口，再并行于产品交付次序接通抖音和目录类渠道；这里描述交付顺序，不授权子 Agent。其余渠道按矩阵逐个 qualification，所有必需地区保留覆盖缺口。下一阶段代码工作需通过本地 OpenSpec 增量扩展合同，不能改旧字段意义。

验收覆盖上游真实形状的脱敏夹具、零值/缩写值、响应包裹、未知 schema、登录过期、服务离线、超时、部分结果、重复批次、后端切换、固定对象复采、跨渠道同作误合并、断源后恢复、旧 card/Profile/Edition 回归。复用现有测试，不新增测试框架；集成证据由现有 runner 生成到 temp/integration-test-runs/，不手写机器回执。

在 Radar 目录执行现有验证命令：

```bash
bun test test/unit/layer-adapters.test.ts
bun run typecheck
bun run test:integration
```

以上是后续实现验收入口，本次设计说明未执行全套测试。真实验收另需具体渠道授权和持续样本；夹具通过、协议接通、真实样本通过、持续资格、DSH 展示、正式发布分别报告。
